# Техническое задание: Task Tracker

## 1. Назначение и границы MVP

Веб-приложение для совместной работы над проектами и задачами. Пользователь создаёт проект, добавляет зарегистрированных коллег по email, распределяет задачи, отслеживает сроки и проводит ревью выполненных работ. Язык интерфейса — русский. Доступно в браузере на телефонах и компьютерах.

В MVP **не входят** отправка email-приглашений, хранение файлов, push-уведомления, OAuth, двухфакторная аутентификация, пользовательские эпики как отдельные сущности, права на уровне отдельных полей и realtime WebSocket. Для доказательств выполнения используется URL (например GitHub, Figma) и текстовое описание.

## 2. Страницы и маршруты

| Страница | URL | Доступ | Возможности |
|---|---|---|---|
| Регистрация | `/register` | Гость | Имя, email, пароль (≥10 символов) |
| Вход | `/login` | Гость | Вход по email/паролю, сессия через JWT-cookie |
| Обзор | `/` | Авторизованный | Статистика проектов, задач, ревью и назначенных задач |
| Проекты | `/projects` | Авторизованный | Список доступных проектов, создание |
| Проект и задачи | `/projects/:id` | Участник проекта / глобальный админ | Серверный HTML-список задач, фильтры, участники, сроки, создание/редактирование согласно роли |
| Администрирование | `/admin` | Глобальный админ | Список пользователей и изменение глобальной роли |
| Справка | `/about` | Все | Описание сценариев и ролей |
| Swagger | `/swagger` | Все | Документация REST API |
| OpenAPI | `/openapi.yaml` | Все | Машинно-читаемая спецификация |

Серверный MVC: маршруты GET обрабатывает Gin и возвращает готовые HTML-страницы через Go `html/template`. HTML-формы работают через POST + CSRF-токен + 303 redirect (Post/Redirect/Get). Никакого JavaScript SPA или History API нет; Nginx проксирует запросы к Go. REST/JSON API отдельно доступен по `/api/*` для Swagger и внешних клиентов.

## 3. Данные (таблицы PostgreSQL)

| Таблица | Основные поля | Ограничения |
|---|---|---|
| `users` | `id`, `name`, `email`, `password_hash`, `role`, `created_at` | Уникальный email; пароль bcrypt; роль `user/admin` |
| `sessions` | `id`, `user_id`, `token_hash`, `expires_at`, `revoked_at`, `created_at` | Уникальный SHA-256 хэш JTI; отозванная сессия недействительна |
| `projects` | `id`, `name`, `description`, `created_by`, `owner_id`, `created_at`, `updated_at` | Создатель неизменен; владелец может передаваться |
| `memberships` | `id`, `project_id`, `user_id`, `role`, `created_at` | Пара `(project_id,user_id)` уникальна; роль `owner/manager/member` |
| `tasks` | `id`, `project_id`, `title`, `description`, `status`, `priority`, `urgency_override`, `tags`, `epic`, `created_by`, `assignee_id`, `due_at`, `completed_at`, `created_at`, `updated_at` | `assignee_id`, `due_at`, `completed_at` nullable; статусы `todo/in_progress/in_review/done` |
| `reviews` | `id`, `task_id`, `submitted_by`, `description`, `evidence_url`, `status`, `reviewer_id`, `comment`, `created_at`, `reviewed_at` | Статусы `pending/approved/rejected`; история ревью сохраняется |

Code First: структуры Go/GORM — источник схемы; `AutoMigrate` запускается при старте API, недеструктивно обновляя таблицы. Каждое изменение должно сопровождаться обновлением схемы API; перед производственной эксплуатацией перейти на версионированные миграции.

## 4. Роли и права

| Операция | Гость | Участник | Управляющий | Владелец | Глобальный админ |
|---|:---:|:---:|:---:|:---:|:---:|
| Регистрация / вход | ✓ | ✓ | ✓ | ✓ | ✓ |
| Посмотреть свой проект | – | ✓ | ✓ | ✓ | ✓ (служебно) |
| Создать собственный проект | – | ✓ | ✓ | ✓ | ✓ |
| Добавить зарегистрированного участника | – | – | ✓ | ✓ | ✓ |
| Создать/редактировать задачу | – | – | ✓ | ✓ | ✓ |
| Начать назначенную задачу | – | ✓ | ✓ | ✓ | ✓ |
| Отправить назначенную задачу на ревью | – | ✓ | ✓ | ✓ | ✓ |
| Проверить чужую работу | – | – | ✓ | ✓ | ✓ |
| Изменить роли участников / передать владение | – | – | – | ✓ | Только если владелец |
| Удалить проект | – | – | – | ✓ | Только если создатель/владелец |
| Назначить глобального админа | – | – | – | – | ✓ |

Примечание: право проверить работу принадлежит управляющему/владельцу, **кроме автора отправки**, даже если он сам управляющий. Исходный создатель проекта также сохраняет право удаления после передачи владения. После передачи новый владелец становится `owner`, предыдущий — `manager`.

## 5. Бизнес-правила

1. Учётная запись уникальна по email. Регистрирующийся получает глобальную роль `user`; через публичный API стать администратором нельзя. Начальный администратор создаётся из защищённых env-переменных.
2. Владелец создаёт проект и автоматически входит в него. Приглашение существующего аккаунта по email сразу добавляет его в проект как `member` (без внешних уведомлений).
3. Только управляющий/владелец может создавать и редактировать задачи, менять приоритет, исполнителя и дедлайн. Назначенный исполнитель может взять `todo` в работу.
4. Задача содержит статус, приоритет, тип/эпик, теги, ответственного, даты создания/окончания и опциональный дедлайн. Приоритет (`low/medium/high/critical`) не равен срочности дедлайна.
5. Индикатор срочности: автоматически зелёный за >7 суток; жёлтый за ≤7 суток; красный за ≤72 часа; мигающий красный за ≤24 часа и при просрочке. `urgency_override` позволяет управляющему принудительно выбрать цвет. При показе задачи вычисляется `effective_priority`: при жёлтом индикаторе не ниже `medium`, красном — `high`, мигающем красном — `critical`; установленное значение `priority` при этом не перезаписывается. После завершения задачи отображается исходный приоритет.
6. Исполнитель может отправить на ревью только назначенную ему задачу в `todo` или `in_progress`. Необходимы описание работы и/или валидная HTTP(S)-ссылка. При отправке создаётся новая запись `review` со статусом `pending`.
7. Проверяющий, отличный от отправителя, принимает (`done`, `completed_at` установлено) или отклоняет (`in_progress`, с комментарием) работу. Переход напрямую в `done` отсутствует. Выполненные задачи неизменяемы в MVP.
8. При исключении участника из проекта его задачи становятся неназначенными; владелец не может удалить себя, пока не передаст роль.
9. Сессии: JWT HS256 в `HttpOnly` cookie `SameSite=Lax` или `Authorization: Bearer`; JTI хранится как SHA-256 в PostgreSQL. TTL 7 дней, logout отзывает текущую сессию. Для запросов со стороннего Origin изменение состояния запрещено.
10. Query-параметры `status`, `priority`, `assignee`, `q` фильтруют задачи; `q` фильтрует проекты. Контроль доступа производится **на сервере**, а не только скрытием кнопок.

## 6. Нефункциональные требования

- Основной сайт — серверный MVC: Go/Gin Controller + GORM Model + HTML View (`html/template`, `embed`). Отдельный REST/JSON API сохранён для Swagger. PostgreSQL и GORM. Разделение reverse proxy, Go и DB через Docker Compose.
- Валидация Gin binding для API, явная проверка HTML-форм, CSRF-токены для POST, а также серверные проверки бизнес-правил. Пароли хранятся только в bcrypt, не возвращаются в HTML/JSON.
- Ошибки API JSON формата `{ "error": "..." }` и соответствующие HTTP-коды.
- Адаптивные серверные HTML-шаблоны и CSS для мобильных экранов, без JavaScript SPA.
- Swagger/OpenAPI 3 документирован для основных endpoints; доступ к защищённым API через bearer/cookie.
- Данные переживают перезапуск контейнеров за счёт Docker volume.
- Кэш статистики in-memory TTL 10 секунд, инвалидируется при изменениях; нет зависимости от Redis.
- Документированный локальный запуск одной командой `docker compose up --build`.
- HTML-страницы формируются сервером из шаблонов Go; после POST-форм используется 303 See Other.

## 7. Критерии приёмки

1. Новый пользователь регистрируется, выходит, повторно входит.
2. Создание проекта создаёт владельца. Добавление существующего пользователя по email работает, повторное добавление возвращает ошибку.
3. Владелец назначает управляющего и передаёт владение; исходный создатель может удалить свой проект.
4. Участник видит проекты, к которым он относится, и не получает доступ к чужим проектам API.
5. Назначенный исполнитель переводит задачу в работу и отправляет доказательство выполнения на ревью.
6. Прямое завершение исполнителем запрещено; саморевью запрещено; при одобрении появляется `completed_at`.
7. Дедлайны отображаются цветом, изменение вручную работает. Поиск и фильтры работают.
8. Глобальный админ управляет ролями через `/admin`, обычный пользователь API администрирования получает 403.
9. `docker compose up --build` запускает сервисы, `GET /health` возвращает `{"ok":true}`.
